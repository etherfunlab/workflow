# Engineering rules

- **KISS.** Three similar blocks of code beat one premature abstraction. No extension points for requirements that do not exist yet, and no defensive checks against trusted internal code.
- **One fact, one authoritative source.** Every fact (a value, a state, a condition) lives in one place; everything else derives from it through a view, a computation or a join. Prefer one more derived query over one more redundant column.
- **Schema comes from migration files; interfaces come from code.** Do not maintain copies of either in documentation; link to the source.
- **Reuse an interface before adding one.** Before adding an endpoint or interface, search for an existing one that does the job. When it is unclear whether logic belongs in frontend middleware or behind a backend endpoint, ask the user before writing it.
- **Tuning lowers the error rate; it does not chase zero.** Driving errors to zero fits the noise of the current corpus and breaks on the next one. A metric that held level is not a to-do.
- **Read live state from releases, not branches.** Check the deploy or release list to know what is running, and decide the rollback path before deploying.
- **Compare regressions by the set of failing test names, not by the count.** An equal count can hide a new regression offset by a flaky test that happened to pass; run the same command on a baseline checked out in a separate worktree.
- **Contract before handler.** Declare the interface contract (schema, DTO, route) before implementing it. Generated API documentation is an artifact, not the source of truth.
- **Foreign keys are decided at table creation.** A column that references another table gets its foreign key in the migration that creates it. Nullability and ON DELETE are one decision: a nullable reference takes SET NULL, a NOT NULL reference can only CASCADE. Index every FK column. A fact the parent id already determines is not stored again.
- **Delete cleanly; the history goes in the commit message.** Removed code, config or documentation leaves no tombstone where it used to be: no "X is deprecated, don't use it", no commented-out old code, no "removed in version N". Why it was removed goes in the commit message. Records of change are not tombstones: release notes and changelogs still state removals, migrations and runbooks keep their preconditions, and a published statement that turned out wrong is still corrected explicitly. The one exception: something that was actually added back after removal keeps one line, "Do not re-add X: reason Y".
- **Default-open, then ratchet the gate.** Open capabilities first to learn the real ceiling and actual usage, and instrument that phase so it leaves a baseline. Tightening raises a threshold — a condition, a tier, a cooldown, a cost — and never removes the capability. Do not tighten before a tested fallback exists.
