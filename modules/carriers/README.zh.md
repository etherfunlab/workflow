# carriers

出自心法：仓库管理、权威唯一、跨仓开单。

## 这是什么

每句话该写在哪：文档正文、commit message、PR 和 issue 留言、release notes 各回答什么问题。写进你仓里的主规则文件（AGENTS.md，没有的话是 CLAUDE.md）。

## 为什么

Git 仓库就是记忆库和上下文库，前提是每类信息放在固定的载体里。正文写进了改稿过程，读者要从流水账里自己拼出现状；证据只留在聊天里，下次就找不到凭什么这么改。载体分工清楚，人和 agent 才知道去哪里找什么。

## 规矩

**载体分工**

| 载体 | 回答什么 |
|---|---|
| 正文 | 现在是什么、为什么是这样 |
| commit message | 这次改了什么、凭什么改：证据链、实测数字、被推翻的旧判断 |
| PR / issue 留言 | 与人的对话：回应审阅意见、立案待办、说明改了哪几处 |
| release notes | 对下游的影响：破坏性变更、升级顺序 |

**改正文，还是补充**

- 事实错了：直接改，理由进 commit message。
- 决策变了：正文只留新决策，旧决策和推翻它的理由进 commit message。
- 有新事实而旧结论仍然成立：补进正文。
- 已经有人评论过：改正文，另外留言说明改了什么。
- 已经发布、可能被引用：改正文，并显式标注勘误。

迁移文件、部署顺序、runbook 这类「以后有人照着做」的文件，前置条件和陷阱写在文件里，照做的人不会去翻 git log。

**其他**

- **产出物只写结果，不写过程。** 代码、注释、正文只写结果和当前状态，不写「我核过了」「初稿写的是 X」「第三版改的」。唯一的例外：错话已经到过读者眼前，新版要明确指出。
- **关 issue 只留一条总结评论，四行以内**：能力叫什么、一句说明、哪个版本或 PR 带的、文档链接。
- **状态从活文档读。** 冻结的基线不当现状用。
- **跨仓的问题，到目标仓开 issue**（出自跨仓开单）。写清复现步骤和期望结果，交给那个仓的 agent 去读。

**文档放在哪**（出自权威唯一）。ADOPT 会问你四个位置：全局 spec 和给人看的文档、功能 spec 和 plan、schema 定义、接口定义。默认分别是 `docs/`、`docs/superpowers/`、`migrations/*.sql`、代码本身。

完整规则在 [`agent/rules/carriers.md`](agent/rules/carriers.md)。

## 装进你仓里的是什么

主规则文件（AGENTS.md，没有的话是 CLAUDE.md）里的一节 `## Carriers`，四个文档位置按你的回答填好。
